# 単元 5-1：主要な脅威と手口（SQLi、BOLA/IDOR、マスアサインメント、認証情報漏洩、DoS）

> **この単元のゴール**
> Web・API で実際に多発している攻撃の手口を、「なぜ成立するのか」から説明でき、Laravel / PHP での具体的な防ぎ方を示せるようになる。

---

## 【概念の解説】

### 0. すべての攻撃に共通する原理

第1章〜第4章を通して見てきたことを一言でまとめると、

> **攻撃とは、「システムが信頼してはいけないものを信頼している箇所」を突くこと。**

| 信頼してはいけないもの | 例 | 突かれると |
|---|---|---|
| 利用者からの入力 | フォームの値、URL、ヘッダー、アップロードファイル、Webhook の中身 | SQLi、マスアサインメント |
| 利用者が指定した ID | `/customers/1234` の `1234` | BOLA / IDOR |
| 「中にいるから安全」という前提 | 社内ネットワーク、同じサーバー | 横展開、内部不正 |
| 「誰にも見られない」という前提 | コード、ログ、Git の履歴 | 認証情報漏洩 |
| 「普通に使われる」という前提 | 想定外の量のリクエスト | DoS |

以下、それぞれの手口を見ていきます。

### 1. SQL インジェクション（SQLi）

**手口**：入力値を SQL 文に文字列として埋め込んでいると、入力値の中に SQL の命令を混ぜられる。

```php
// 危険：入力をそのまま SQL に連結
$name = $_GET['name'];
$rows = DB::select("SELECT * FROM customers WHERE name = '$name'");
```

攻撃者が `name` に `' OR '1'='1` を入れると、SQL は次のようになります。

```sql
SELECT * FROM customers WHERE name = '' OR '1'='1'
-- '1'='1' は常に真 → 全顧客が返る
```

さらに `'; DROP TABLE customers; --` のような入力で、データの破壊を狙われることもあります（DB や接続方法によっては、複数の文を一度に実行できる）。

**なぜ成立するか**：DB から見ると、「どこまでがプログラマーの書いた命令で、どこからが利用者の入力か」の区別がつかないから。

**対策**：**プリペアドステートメント（プレースホルダ）**。SQL の「形」と「値」を別々に DB に送るので、値の中に何が書かれていても命令として解釈されない。

```php
// 安全：値はプレースホルダで渡す
$rows = DB::select('SELECT * FROM customers WHERE name = ?', [$name]);
// Eloquent / クエリビルダも内部でプレースホルダを使う
$rows = Customer::where('name', $name)->get();
```

**Laravel でも危ない書き方**：`whereRaw()`、`DB::raw()`、`orderBy($request->sort)` のように、**生の SQL や列名に入力を入れる**箇所。列名や並び順はプレースホルダにできないので、**許可リスト**（`in_array($sort, ['name', 'created_at'])`）で検証する。

**被害を小さくする多層防御**：単元3-5のロール分離。アプリのロールに `DROP` や `DELETE` 権限がなければ、SQLi を突かれても破壊はできない。

### 2. BOLA / IDOR（オブジェクトレベルの認可の不備）

**手口**：ログインした利用者が、URL や API のパラメータの ID を書き換えて、**他人のデータ**にアクセスする。

```text
GET /api/customers/1234   ← 自分の担当顧客
GET /api/customers/1235   ← ID を1つ増やしただけで他人の担当顧客が見えた
```

API のセキュリティの専門家団体 OWASP がまとめた「API セキュリティ上位10項目」で、**第1位**に挙げられている、最も多い脆弱性の1つです（BOLA：Broken Object Level Authorization。IDOR：Insecure Direct Object Reference とも呼ばれる）。

**なぜ成立するか**：「**ログインしているか（認証）**」は確認しているが、「**この人がこのデータを見てよいか（認可）**」を確認していないから。

```php
// 危険：ログインさえしていれば、どの顧客でも返す
public function show($id) {
    return Customer::findOrFail($id);
}

// 安全：その利用者がアクセスしてよいかを毎回確認する
public function show(Customer $customer) {
    $this->authorize('view', $customer);   // Policy で「担当部署が同じか」などを判定
    return $customer;
}
```

**多層防御**：

- ID を推測しにくい UUID にする（単元3-4）→ 推測は難しくなるが、**ID が漏れれば同じ**なので、認可チェックの代わりにはならない
- DB の行レベルセキュリティ（単元3-5）→ アプリのチェック漏れを DB 側で止める

### 3. マスアサインメント

**手口**：フォームから送られた値を**まとめて**モデルに代入する機能を悪用し、**本来変更できない項目**を書き換える。

```php
// 危険：送られてきた値を全部そのまま保存
$user->update($request->all());
```

画面には「名前」と「電話番号」の入力欄しかなくても、攻撃者は HTTP リクエストを自分で作れる（単元2-4）ので、次のように送れます。

```http
PATCH /api/profile
Content-Type: application/json

{"name": "山田", "phone": "03-...", "role": "admin", "department_id": 1}
```

**なぜ成立するか**：「画面に入力欄がない＝送られてこない」と思い込んでいるから。**画面は利用者の手元で自由に改造できる**。

**対策**：変更してよい項目を**許可リストで明示**する。

```php
// モデルで許可する項目を限定
protected $fillable = ['name', 'phone'];

// さらに、バリデーション済みの値だけを使う
$user->update($request->validated());
```

### 4. 認証情報の漏洩

**手口**：パスワード、APIトークン、DB の接続情報、クラウドの鍵などが、意図しない場所から漏れる。

| 漏れる場所 | 典型例 |
|---|---|
| **Git リポジトリ** | `.env` をコミットした。**一度コミットすると、削除しても履歴に残る**。公開リポジトリは、秘密情報を探すボットに数分でスキャンされる |
| **ログ** | API のリクエスト全体（ヘッダーの認証トークンを含む）をログに出した（単元1-3） |
| **URL** | `?api_key=...` をクエリに入れ、アクセスログ・ブラウザ履歴・リファラから漏れた（単元2-4） |
| **コンテナイメージ** | Dockerfile で秘密情報をコピーし、イメージを公開レジストリに置いた |
| **チャット・メール** | 「とりあえずこれ使って」と Slack に貼った |
| **フィッシング** | 偽のログイン画面にパスワードを入力させられた |

**対策**：

- 秘密情報は **Secret Manager** に保管し、コードや Git に置かない（単元5-2）
- `.gitignore` に `.env` を入れる。GitHub の **Secret scanning / Push protection** を有効にする
- **漏れた（かもしれない）と分かったら、削除ではなく「無効化して再発行（ローテーション）」**。Git の履歴から消しても、すでに誰かがコピーしているかもしれない
- 人間のアカウントには **多要素認証（MFA）** を必須にする（パスワードが漏れても突破されにくい）

### 5. DoS（サービス妨害）

**手口**：大量のリクエストや重い処理を送りつけて、正規の利用者が使えない状態にする。

| 種類 | 例 |
|---|---|
| 量で押す | 大量のリクエスト。複数の乗っ取られた端末から一斉に送る場合は **DDoS** |
| プロトコルの弱点 | SYN フラッド（単元2-2） |
| **アプリの重い処理を狙う** | 検索に `%` だけを入れて全件スキャンさせる。巨大なファイルをアップロードする（単元4-2）。ページ番号に `999999999` を指定する |
| **お金を狙う**（クラウド特有） | 自動でスケールするサービスに大量アクセスし、**利用料を膨らませる** |

**対策**：

- 入口（ロードバランサー＋WAF）での **レート制限**、DDoS 対策（単元5-2）
- アプリでの上限設定：ページサイズの上限、アップロードサイズの上限、検索条件の必須化、タイムアウト
- Cloud Run の **最大インスタンス数** の設定、**予算アラート**（第7章）

## 【実務・ビジネスとの結びつき】

### これが理解できていないと起きること

| 現場の症状 | 根本原因 |
|---|---|
| 「検索窓に変な文字を入れられて、全顧客の情報が抜かれた」 | SQL の文字列連結（SQLi） |
| 「顧客ポータルで、他社の請求書が見られると通報があった」 | 認可チェックの欠落（BOLA / IDOR） |
| 「一般社員が、いつの間にか管理者権限を持っていた」 | マスアサインメント |
| 「GitHub に上げた翌日、クラウドの請求が数百万円になっていた」 | 公開リポジトリにクラウドの鍵をコミットし、仮想通貨の採掘に悪用された |
| 「深夜にアクセスが急増し、サービスが止まって、請求も跳ね上がった」 | レート制限・最大インスタンス数・予算アラートがない |

### 顧客のどの課題を解決するか

- 中小企業向けの受託開発では、セキュリティ対策が「見積もりに含まれていない」「何をしているか説明されない」ことが多い。**具体的な脅威と、それぞれへの対策を一覧で示せる**ことは、価格競争ではない差別化になる。
- 経営者が恐れているのは「技術的な脆弱性」ではなく、「**取引先や顧客からの信用失墜、損害賠償、業務停止**」。この単元の手口を、そうした経営リスクの言葉に翻訳して伝えることが重要（第8章）。

## 【顧客向け言語化トレーニング】

専門用語（SQLインジェクション、IDOR、認可、DoS 等）を使わずに答えてください。

**演習1**
> 社長「うちみたいな小さな会社を、わざわざハッカーが狙うかね？」

**演習2**
> 社長「セキュリティにお金をかけろって言うけど、何にいくらかかって、何が防げるのか分からないと判断できないよ。」

<details>
<summary>💡 回答のヒント（考えてから開く）</summary>

- 演習1：攻撃の多くは「狙って」いるのではなく、**機械が自動でインターネット上の全部を順番に試している**。会社の大小は関係なく、鍵の開いている家から入られる。さらに「取引先の大企業に入るための踏み台」として小さな会社が狙われることもある。脅すのではなく、事実として淡々と伝える。
- 演習2：「何が起きると、いくら損するか」から逆算する。例えば「顧客情報が漏れたら、お詫び・調査・報告・取引停止でいくら」「1日止まったら売上がいくら」。そのうえで、対策を「必ずやるべき基本（費用小・効果大）」と「必要に応じて追加するもの」に分けて提示する。保険のような考え方。

</details>
