# 単元 3-5：DB セキュリティ（権限分離、行レベルセキュリティ、暗号化、監査ログ）

> **この単元のゴール**
> 「DB にログインできた人（プログラム）が、何でもできてしまう」状態を避けるための設計ができるようになる。万が一のときに「誰が何をしたか」を追える仕組みを説明できるようになる。

---

## 【概念の解説】

### 1. よくある危険な状態：全員が「管理者」で接続している

小規模なシステムでは、次のような構成が珍しくありません。

```text
Web アプリ     ──┐
取り込みバッチ  ──┼── すべて postgres（管理者）ユーザーで接続
分析ツール      ──┤
開発者の手作業  ──┘
```

この状態で、Web アプリに SQL インジェクション（第5章）の脆弱性があったとします。攻撃者はアプリの接続ユーザーとして SQL を実行できるので、

- 全テーブルの読み出し（顧客情報の大量流出）
- `DROP TABLE`（全データ削除）
- 新しい管理者ユーザーの作成（裏口）

がすべて可能になります。単元1-2で学んだ「**乗っ取られたら、そのユーザーの権限でできることは全部できる**」が、DB でもそのまま当てはまります。

### 2. ロール（ユーザー）を用途ごとに分ける

PostgreSQL では、ユーザーもグループも **ロール** という仕組みで管理します。このカリキュラムの構成では、次のように分けます。

| ロール | 使う人・プログラム | できること | できないこと |
|---|---|---|---|
| `app_owner` | マイグレーション（テーブル作成・変更）のときだけ | テーブルの作成・変更 | 普段は使わない。ログイン情報は厳重に保管 |
| `app_rw` | Web アプリ、取り込み処理 | 業務テーブルの読み書き | テーブル削除、構造変更、権限変更 |
| `etl_reader` | BigQuery への同期処理 | 必要なテーブルの読み取りのみ | 書き込み |
| `analyst_ro` | 社内の分析担当（必要な場合のみ） | 個人情報を除いたビューの読み取りのみ | 元テーブルへのアクセス |

```sql
-- ロールの作成（パスワードは Secret Manager で管理する。第5章）
CREATE ROLE app_rw     LOGIN PASSWORD '...';
CREATE ROLE etl_reader LOGIN PASSWORD '...';

-- 既定でみんなに与えられている権限を取り上げる
REVOKE ALL ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON DATABASE salesdb FROM PUBLIC;

-- 必要な権限だけを与える
GRANT CONNECT ON DATABASE salesdb TO app_rw, etl_reader;
GRANT USAGE ON SCHEMA public TO app_rw, etl_reader;
GRANT SELECT, INSERT, UPDATE ON customers, orders, order_items TO app_rw;  -- DELETE は与えない
GRANT SELECT ON customers, orders, order_items, products TO etl_reader;
```

`app_rw` に `DELETE` を与えていない点に注目してください。業務上「削除」が必要なら、ステータスを `cancelled` にする（論理削除）設計にすれば、**アプリが乗っ取られても物理的な削除はできない**状態にできます。

### 3. ビューで「見せる列」を絞る

分析担当には、電話番号や住所までは不要なことがほとんどです。**ビュー**（保存された SELECT 文）を作り、ビューにだけ権限を与えます。

```sql
CREATE VIEW v_customers_masked AS
SELECT id,
       name,
       substring(address from '^(北海道|東京都|京都府|大阪府|.{2,3}?県)')
           AS prefecture,                -- 都道府県だけ
       created_at
FROM customers;

GRANT SELECT ON v_customers_masked TO analyst_ro;
-- analyst_ro には customers テーブル本体の権限を与えない
```

### 4. 行レベルセキュリティ（RLS）：見せる「行」を絞る

ロールとビューは「どのテーブル・どの列か」を制御しますが、「**同じテーブルの中で、どの行を見せるか**」を制御したい場合があります。例えば、

- 営業担当者は**自分の担当顧客だけ**見られる
- 複数の拠点（支店）が同じ DB を使うが、**自拠点のデータだけ**見られる

これを DB の機能で強制するのが **行レベルセキュリティ（Row Level Security, RLS）** です。

```sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;

-- アプリは接続後に「今の利用者の拠点」を設定する
--   SET app.branch_id = '3';
CREATE POLICY branch_isolation ON customers
    USING (branch_id = current_setting('app.branch_id')::bigint);
```

RLS を有効にすると、`SELECT * FROM customers` と書いても、**DB が自動的に自拠点の行だけに絞り込みます。** アプリの実装で `WHERE branch_id = ?` を書き忘れても、他拠点のデータは漏れません。

> **注意点**：テーブルの所有者や、`BYPASSRLS` 属性を持つロール（管理者など）には、既定では RLS が適用されません。アプリは所有者とは別のロール（`app_rw`）で接続する、という第2節の設計が前提になります。

### 5. 暗号化：3つの場面

| 場面 | 守る相手 | 方法 |
|---|---|---|
| **通信中**（in transit） | 経路上の盗聴者 | TLS。`sslmode=verify-full`（単元2-4） |
| **保存時**（at rest） | ディスクやバックアップの盗難 | Cloud SQL はストレージを既定で暗号化。鍵を自社で管理したい場合は顧客管理の暗号鍵（CMEK） |
| **列単位** | DB にアクセスできる人（管理者を含む） | マイナンバーなど特に機密性の高い列だけ、アプリ側や `pgcrypto` で暗号化する |

**保存時の暗号化の限界**を理解しておくことが重要です。ディスクの暗号化は、「ディスクを物理的に盗まれた」場合には有効ですが、**DB に正規にログインした人（や乗っ取ったプログラム）には、復号済みのデータが普通に見えます。** 単元1-1の Q3 の論点そのものです。だから権限分離と RLS が必要になるのです。

> **パスワードは「暗号化」ではなく「ハッシュ化」する。** 暗号化は元に戻せる（鍵があれば復号できる）が、ハッシュ化は元に戻せない。ログイン用パスワードは bcrypt / Argon2 などでハッシュ化して保存する（Laravel の `Hash::make()` はこれ）。

### 6. 監査ログ：「誰が・いつ・何をしたか」

どれだけ守っても、侵害をゼロにすることはできません。だから **起きたときに気づき、範囲を特定できる** ことが重要です。

| 記録するもの | PostgreSQL / Cloud SQL での方法 |
|---|---|
| 接続・切断（誰がどこから） | `log_connections`、`log_disconnections` |
| 実行された SQL（特に DDL・権限変更） | `log_statement = 'ddl'`、`pgaudit` 拡張（Cloud SQL で利用可能） |
| 管理操作（インスタンスの設定変更など） | Google Cloud の Cloud Audit Logs |
| アプリ上の操作（誰がどの顧客を見たか） | アプリ側で操作ログテーブルに記録 |

注意点：

- **ログ自体に個人情報やパスワードが含まれないようにする**（`log_statement = 'all'` は SQL に含まれる値まで記録する）
- **ログは DB とは別の場所に保管する**（攻撃者が DB の管理者権限を取ると、DB 内のログは消せる）

## 【実務・ビジネスとの結びつき】

### これが理解できていないと起きること

| 現場の症状 | 根本原因 |
|---|---|
| 「小さな脆弱性から、全顧客データが流出し、テーブルも消された」 | アプリが管理者ユーザーで DB に接続していた |
| 「A支店の担当者に、B支店の顧客リストが見えていた」 | アプリ側の絞り込み漏れ。RLS などの DB 側の強制がなかった |
| 「漏洩が発覚したが、いつから・何件漏れたか分からず、報告できない」 | 監査ログがない、または DB と一緒に消された |
| 「分析用に渡したデータに、全顧客の電話番号が入っていた」 | 分析用ロールに元テーブルの権限を与えていた |

### 顧客のどの課題を解決するか

- 個人情報保護法では、漏洩が起きたときに個人情報保護委員会への報告や本人への通知が求められる場合がある（第7章）。**「何件、誰のデータが」を特定できる監査ログ**は、そのときの会社の信用と対応コストを大きく左右する。
- 「社員全員が全データを見られる」状態から「**役割ごとに見られる範囲を DB が強制する**」状態への移行は、経営者にとって分かりやすいセキュリティ向上であり、退職者・内部不正への対策としても訴求できる。

## 【理解度チェック課題】

**Q1.**
Web アプリ・取り込み処理・BigQuery 同期処理がすべて同じ管理者ユーザーで DB に接続している構成の問題点を説明し、どう改善すべきか提案してください。

**Q2.**
「Cloud SQL はディスクが暗号化されているので、顧客データは安全です」という説明の、正しい部分と不十分な部分をそれぞれ答えてください。

**Q3.**
行レベルセキュリティ（RLS）を使うと、アプリ側で絞り込み条件を書く場合と比べて何が良いのですか。また、RLS を設定しても効かないケースを1つ挙げてください。
