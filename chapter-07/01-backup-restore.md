# 単元 7-1：バックアップとリストア（RPO / RTO）

> **この単元のゴール**
> 「データが消えた・壊れた・人質に取られた」ときに、**どこまで戻せて、どれくらいで復旧できるか**を、顧客と合意できる形で設計・説明できるようになる。

---

## 【概念の解説】

### 1. 「冗長化」と「バックアップ」は別物

よくある誤解から始めます。

> 「Cloud SQL は高可用性構成（HA）にしてあるので、バックアップは大丈夫です」

これは**間違い**です。

| 仕組み | 目的 | 守れるもの | 守れないもの |
|---|---|---|---|
| **高可用性（HA）・レプリカ** | 止まらないこと（可用性） | サーバーやゾーン（データセンターの区画）の故障 | **誤操作・バグ・攻撃によるデータの破壊** |
| **バックアップ** | 元に戻せること（復旧性） | 誤操作・バグ・攻撃・論理的な破損 | （リストアには時間がかかるので）止まらないことは保証しない |

HA やレプリカは、単元3-1で学んだ WAL を使って、変更を**即座に**複製します。つまり、誰かが `DELETE FROM customers;` を実行すると、その削除も**即座にレプリカに複製されます**。ランサムウェアがデータを暗号化した場合も同じです。

> **冗長化は「故障」から守り、バックアップは「間違い」から守る。** 両方が必要です。

### 2. RPO と RTO：顧客と合意する2つの数字

| 指標 | 意味 | 問い |
|---|---|---|
| **RPO**（Recovery Point Objective：目標復旧時点） | **どの時点まで**データを戻せればよいか ＝ どれだけのデータ損失を許容できるか | 「障害が起きたとき、最大で何時間分のデータが消えても業務を続けられますか？」 |
| **RTO**（Recovery Time Objective：目標復旧時間） | **どれくらいの時間で**復旧すればよいか ＝ どれだけの停止を許容できるか | 「システムが止まったら、何時間以内に再開しないと業務に支障が出ますか？」 |

```text
           RPO                          RTO
    ←────────────→              ←────────────→
───●───────────────●───────────●────────────────●───→ 時間
 最後に戻せる時点    障害発生     復旧作業開始        業務再開
  （ここまでは戻る）  ↑ この間のデータは失われうる
```

RPO・RTO を短くするほど、費用と運用の手間は増えます。**技術者が勝手に決めるものではなく、業務への影響と費用を示して、顧客に選んでもらう**ものです。

| 例 | RPO | RTO | 必要な仕組み |
|---|---|---|---|
| 分析用のデータ（BigQuery） | 1日 | 1〜2日 | raw から作り直せれば十分 |
| 受注・顧客の正データ（PostgreSQL） | 数分 | 数時間 | 自動バックアップ ＋ ポイントインタイムリカバリ |
| 止まると売上が止まる EC の在庫 | ほぼ0 | 数分 | HA ＋ PITR ＋ 手順化された切り替え |

### 3. PostgreSQL（Cloud SQL）のバックアップ

| 仕組み | 内容 |
|---|---|
| **自動バックアップ** | 1日1回、DB 全体のスナップショットを取得し、決めた期間保持する |
| **ポイントインタイムリカバリ（PITR）** | バックアップ ＋ その後の **WAL**（単元3-1）を保管しておき、「**昨日の 14:32 の状態**」のように、保持期間内の任意の時点に戻せる |
| **オンデマンドバックアップ** | 大きな変更（マイグレーション、データ移行）の直前に手動で取る |
| **エクスポート** | `pg_dump` 形式などでファイルに書き出し、Cloud Storage に保管する。別のプロジェクトや別の環境への持ち出しにも使える |

保持期間や細かい挙動は、Cloud SQL のエディションや設定によって異なるので、案件ごとに公式ドキュメントで確認して決めます。

**PITR が特に効く場面**：誤操作による一括更新・削除。「14:35 に誤って全顧客のランクを C に更新してしまった」→ 14:34 の状態を**別のインスタンスとして復元**し、必要なデータだけを本番に戻す。

> **リストアは、本番を上書きするのではなく、別の場所に復元してから必要な部分を戻す**のが基本です。本番をいきなり上書きすると、障害発生後に入力された正しいデータまで失います。

### 4. BigQuery の復旧手段

| 仕組み | 内容 |
|---|---|
| **タイムトラベル** | 過去数日間（既定 7 日。設定で短くできる）のテーブルの状態を、SQL で参照・復元できる：`SELECT * FROM mart.sales_wide FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)` |
| **テーブルスナップショット** | 特定時点のテーブルを、低コストで長期保存する |
| **raw からの再構築** | 単元6-3の層の設計の真価。staging・mart が壊れても、**raw が残っていれば SQL を再実行するだけで作り直せる** |

### 5. ランサムウェアと「バックアップの守り方」

最近のランサムウェア攻撃は、本番データを暗号化する**前に、バックアップを探して消す**のが定石です。バックアップを取っていても、本番と同じ権限で消せる場所にあれば意味がありません。

| 原則 | 具体策 |
|---|---|
| **3-2-1 ルール** | データのコピーを**3つ**持ち、**2種類**の媒体・方式で、**1つ**は別の場所に置く |
| **権限を分ける** | バックアップの削除権限を、本番を操作するアカウント・サービスアカウントに持たせない（単元5-4）。エクスポートは**別のプロジェクト**に置く |
| **消せない期間を設ける** | Cloud Storage の保持ポリシー（一定期間、誰も削除できない設定）を使う |
| **削除保護** | Cloud SQL インスタンスの削除保護を有効にする |

### 6. 「リストアできること」を確かめる

**一度もリストアを試したことのないバックアップは、存在しないのと同じ**です。

- 定期的（例：四半期に1回）に、バックアップから**別環境に実際に復元**し、データが読めるか、何分かかったかを記録する
- 復旧の手順書（ランブック）を作り、担当者以外でも実行できるようにする
- 測った復旧時間が、合意した RTO に収まっているかを確認する

## 【実務・ビジネスとの結びつき】

### これが理解できていないと起きること

| 現場の症状 | 根本原因 |
|---|---|
| 「誤って全件削除したら、レプリカからも消えていた」 | 冗長化とバックアップを混同していた |
| 「バックアップから戻そうとしたら、ファイルが壊れていて戻せなかった」 | 一度もリストアを試していなかった |
| 「ランサムウェアに、本番とバックアップの両方を暗号化された」 | バックアップを本番と同じ権限で削除・変更できる場所に置いていた |
| 「障害時、社長に"いつ復旧するのか、どこまで戻るのか"と聞かれて答えられなかった」 | RPO・RTO を事前に合意していなかった |

### 顧客のどの課題を解決するか

- 中小企業の多くは「社内サーバーのデータを、外付け HDD に、担当者が気が向いたときにコピー」という状態にある。**自動・世代管理・別の場所・復旧の訓練済み**という状態に変えることは、事業継続（BCP）の観点で経営者に響く。
- RPO・RTO を顧客と合意し、**保守契約の SLA**（単元7-4）に落とし込むことで、責任範囲を明確にできる。

## 【理解度チェック課題】

**Q1.**
「Cloud SQL を高可用性構成にしているので、バックアップは不要」という考えの誤りを、具体的な障害の例を挙げて説明してください。

**Q2.**
RPO と RTO の違いを説明してください。また、「受注データの RPO を 1 日」と合意した場合、どんな事態が起こりうるか、顧客の業務に即して説明してください。

**Q3.**
誤操作で `customers` テーブルの一部の列を一括で書き換えてしまいました（発生から30分後に発覚）。PITR を使ってどう復旧しますか。本番を直接、過去の時点に戻してはいけない理由も答えてください。

## 【顧客向け言語化トレーニング】

専門用語（バックアップ、RPO、RTO、冗長化等）を使わずに答えてください。

**演習1**
> 社長「もしデータが全部消えたら、どうなるの？ 元に戻せるの？」

**演習2**
> 社長「バックアップって、毎日取ってるんでしょ？ なら安心だよね？」

<details>
<summary>💡 回答のヒント（考えてから開く）</summary>

- 演習1：「戻せます」だけでなく、「どの時点まで」「何時間で」を具体的に。例：「最大で5分前の状態まで、半日以内に戻せる設計にしています。半年に1回、実際に戻す訓練をして時間を測っています」。数字と訓練の実績が安心につながる。
- 演習2：「毎日取っている」ことと「確実に戻せる」ことは別だと伝える。①その日の途中のデータは戻らない可能性（必要ならもっと細かく戻せる仕組みを提案） ②泥棒（攻撃者）がバックアップまで消そうとするので、別の金庫に分けて保管している ③実際に戻せるかを定期的に試している、の3点。

</details>
