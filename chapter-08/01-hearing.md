# 単元 8-1：仮想クライアントへのヒアリング

> **この単元のゴール**
> 顧客の「困っていること」を、データ基盤の設計に必要な情報（データ源・量・頻度・利用者・制約）にまで掘り下げて聞き出せるようになる。技術の話を急がず、**業務と経営の言葉で**会話できるようになる。

---

## 【概念の解説】

### 1. ヒアリングの目的は「売り込み」ではなく「診断」

医者が、薬を出す前に問診と検査をするのと同じです。最初の面談で構成図や見積もりを出そうとすると、顧客の本当の課題からずれた提案になり、失注するか、受注しても後で揉めます。

ヒアリングで明らかにしたいことは、次の5つです。

| 観点 | 問い | 設計への影響 |
|---|---|---|
| **① 現状（As-Is）** | 今、どのデータを、どこで、誰が、どう扱っているか | データ源・取り込み方法（第4章） |
| **② 課題** | 何に困っているか。それは**誰の・どれくらいの**痛みか | 優先順位、ROI（単元7-3） |
| **③ 理想（To-Be）** | 解決したら、誰が・何を見て・どう行動が変わるか | ダッシュボードの設計（単元6-5）、指標の定義（単元6-4） |
| **④ 制約** | 予算、期限、社内の体制、守るべきルール | 構成の選択、フェーズ分け |
| **⑤ 意思決定** | 誰が決めるか、何を基準に決めるか | 提案書の書き方、誰に何を説明するか |

### 2. 仮想クライアント：株式会社ミナト部品

この章を通して、次の会社を相手に演習します（架空の会社です）。

| 項目 | 内容 |
|---|---|
| 業種 | 機械部品の卸売（取引先は町工場・設備メーカーなど約 800 社） |
| 規模 | 社員 45 名（営業 15 名、営業事務 6 名、経理 3 名、倉庫 15 名、管理 6 名）、年商 約 18 億円 |
| 所在地 | 本社（東京都大田区）、営業所（大阪） |
| 相談者 | 二代目の社長（48歳）。先代から継いで3年目 |
| 最初の問い合わせ内容 | 「データがバラバラで、会議のたびに資料作りに追われている。DX をしたいが、何から手をつければいいか分からない」 |

### 3. 質問の型：広く → 深く → 数字

**① 広く聞く（開いた質問）**

- 「最近、一番困っていらっしゃることは何ですか？」
- 「毎月の会議の資料は、どなたが、どうやって作っていますか？」

**② 深く聞く（なぜ・具体的には）**

- 「それは、具体的にはどんな場面で困りますか？」
- 「その結果、何が起きていますか？」
- 「それが解決すると、社長は何ができるようになりますか？」

**③ 数字にする（量・頻度・時間・金額）**

- 「その作業に、毎月どれくらいの時間がかかっていますか？ 何人で？」
- 「顧客は何社くらい、受注は月に何件くらいですか？」
- 「その数字がずれていたことで、実際に困ったことはありますか？ どれくらいの損失でしたか？」

数字は、見積もり（単元7-3）と ROI の根拠になります。**数字を自分で推測で埋めず、顧客の口から聞く**ことが大切です。

### 4. 観点別の質問リスト

**データ源について（第4章の設計に直結）**

| 質問 | 確認したいこと |
|---|---|
| 顧客・受注・売上・在庫の情報は、それぞれどこで管理していますか？ | データ源の一覧（kintone、Excel、販売管理ソフト、会計ソフト…） |
| そのデータは、誰が入力していますか？ 二重入力はありますか？ | 正となるデータはどこか、現場の負担 |
| データの件数は？ 過去何年分ありますか？ | 移行の量（単元4-2）、ストレージ |
| 使っている SaaS のプラン・契約は？ API は使えますか？ | 連携の可否・制限（単元4-1） |
| Excel はファイルが1つですか？ 担当者ごと・月ごとに分かれていますか？ | クレンジングの手間 |
| 同じ取引先が、システムごとに違う名前で登録されていませんか？ | 名寄せの必要性（単元4-2） |

**利用・目的について（第6章の設計に直結）**

| 質問 | 確認したいこと |
|---|---|
| 毎週・毎月、必ず見ている数字は何ですか？ | ダッシュボードの最初の画面（単元6-5） |
| その数字を見て、何を判断・指示していますか？ | 見たあとの行動 |
| 「売上」はいつの時点で数えていますか？ 部署によって違いますか？ | 指標の定義（単元6-4） |
| 誰が、どの範囲の数字を見てよいですか？ | 権限設計（単元3-5・6-5） |

**制約・体制について**

| 質問 | 確認したいこと |
|---|---|
| 社内に IT を担当している方はいますか？ | 運用の引き継ぎ先、保守の範囲 |
| いつまでに、何ができていると嬉しいですか？ | フェーズ分け |
| 予算の目安はありますか？（ない場合：同じような投資で、過去にいくら使いましたか？） | 構成の選択 |
| 社外の誰か（取引先・銀行・親会社）から求められているルールはありますか？ | セキュリティ・法務の要件（第7章） |
| 最終的に、どなたが導入を決めますか？ | 意思決定者 |

### 5. ヒアリングで気をつけること

| やること | やらないこと |
|---|---|
| 顧客の言葉で話す（「受注」「得意先」など、顧客が使う用語に合わせる） | 専門用語で圧倒する |
| 現状のやり方に敬意を払う（「その Excel で今まで回してこられたのは、〇〇さんの工夫があったからですね」） | 現状を否定する（「Excel なんて古いです」） |
| 「なぜ」を3回くらい掘る | 最初に言われた要望をそのまま受け取る |
| 分からないことは「確認して後日お答えします」 | その場で推測で答える・安請け合いする |
| 実物を見せてもらう（Excel、kintone の画面） | 口頭の説明だけで判断する |
| 最後に、聞いた内容を要約して確認する | 聞きっぱなしで帰る |

## 【実務・ビジネスとの結びつき】

### これが理解できていないと起きること

| 現場の症状 | 根本原因 |
|---|---|
| 「立派なダッシュボードを作ったのに、社長が見てくれない」 | 社長が実際に何を判断しているかを聞かずに作った |
| 「受注後に、想定していなかった Excel が大量に出てきて、移行が終わらない」 | データ源と量を、実物を見て確認しなかった |
| 「担当者は乗り気だったのに、社長の一言で白紙になった」 | 意思決定者と判断基準を確認していなかった |
| 「見積もりが高いと言われた」 | 顧客の痛みの大きさ（ROI）を数字で聞き出していなかった |

### 顧客のどの課題を解決するか

- 多くの中小企業は「DX したい」とは言えても、**何が課題かを自分で整理できていない**。ヒアリングを通して課題を言語化してあげること自体が、顧客にとって大きな価値になる。
- プログラミングスクールの講師として、受講生のつまずきを聞き出してきた経験は、そのままヒアリングの力になる。

## 【理解度チェック課題】

**Q1.**
ヒアリングで明らかにすべき5つの観点を挙げ、それぞれが設計・提案のどこに影響するか説明してください。

**Q2.**
社長から「データを一元化したい」と言われました。この要望を、そのまま受け取らずに掘り下げるための質問を3つ考えてください。

**Q3.**
ヒアリングで、データの「件数」「入力者」「二重入力の有無」を必ず確認すべき理由を、第4章の内容と結びつけて説明してください。

## 【顧客向け言語化トレーニング】

**演習（ロールプレイ）**

講師（Claude）が **株式会社ミナト部品の社長** 役を務めます。あなたはヒアリングを行うコンサルタントです。

**進め方**

1. チャットで「単元8-1のロールプレイを始めます」と伝えてください
2. 社長への質問を1つずつ送ってください。社長は、**聞かれたことにだけ**答えます（聞かれていないことは自分から話しません）
3. 15〜20往復を目安に、上の「ヒアリングシート」が埋まるまで質問してください
4. 最後に「ヒアリングを終了します」と伝え、聞き取った内容をヒアリングシートの形でまとめて送ってください
5. 講師がフィードバックします：聞き出せた情報 / 聞き漏らした重要な情報 / 質問の仕方の良かった点・改善点

> **ヒント**：社長は、最初は「会議の資料作りが大変」としか言いません。その奥に、もっと深刻な問題がいくつか隠れています。「なぜ」と「数字」で掘り下げてください。
